# Интеграция Modx3ProfilerToolbar с pdoTools

## Общие сведения

Modx3ProfilerToolbar автоматически собирает информацию о выполнении сниппетов и чанков, обработанных pdoTools, включая Fenom-шаблоны.

## Механизм интеграции

### Для MODX 3 / pdoTools 3.x

**Метод:** перехват и парсинг встроенного лога `CoreTools::$timings` через Reflection API.

**Как работает:**
1. При завершении запроса (`OnWebPagePrerender`) Modx3ProfilerToolbar получает доступ к внутреннему массиву `CoreTools::$timings` через Reflection
2. Парсит записи с сообщениями `Loaded "modSnippet" with name "{name}"`
3. Каждая такая запись считается выполненным сниппетом и добавляется в статистику

**Код:** `ProfilerService::collectCoreToolsTags()`, `getPdoToolsTimings()`, `parsePdoToolsTimings()`

## Что профилируется

✅ **Работает:**
- Все сниппеты, выполняемые через pdoTools (`$_modx->runSnippet()`, Fenom-вызовы типа `{$_modx->runSnippet('ms3ProductSets')}`)
- Отображение количества вызовов сниппетов
- Отображение имён сниппетов в тулбаре и админке

❌ **Не профилируется:**
- **Время выполнения сниппетов:** в логе pdoTools фиксируется только время загрузки элемента из БД, но не его реального выполнения
- **Запросы SQL внутри сниппетов:** pdoTools не передаёт информацию о запросах, выполненных внутри сниппетов
- **Чанки Fenom:** хотя Fenom обрабатывается pdoTools, в логе нет явной привязки чанков к их обработке (есть только "Compiled Fenom chunk")

## Ограничения и почему

### 1. Почему не используется `debugPdoParser` интерфейс?

**Причина:** В pdoTools 3.x проверка `if ($this->modx->parser instanceof debugPdoParser)` в методе `debugParser()` является **устаревшей** и никогда не выполняется. Этот механизм работал в pdoTools 2.x для MODX 2.x.

**Код в CoreTools.php (строка 1342):**
```php
protected function debugParser($tag)
{
    if ($this->modx->parser instanceof debugPdoParser) {
        // Никогда не выполняется в MODX 3 / pdoTools 3.x
    }
}
```

### 2. Почему нет точного времени выполнения?

**Причина:** Массив `CoreTools::$timings` содержит записи только о **загрузке** элементов из БД, но не об их **выполнении**. Время, указанное в timings — это время операции `modX->getObject()`, а не `runSnippet()`.

**Пример:**
```
Loaded "modSnippet" with name "ms3ProductSets"  // ← время загрузки ~0.006s
(сниппет выполняется, делает 50 SQL-запросов, работает 0.5s)  // ← НЕ логируется
```

### 3. Почему нельзя перехватить парсер или pdoTools?

**Попытки (не сработали):**
- ✗ Подмена `$modx->parser` на обёртку `Modx3ProfilerToolbarParser` — ломает Fenom, т.к. pdoTools кэширует ссылку на парсер в `OnMODXInit`
- ✗ Замена `pdotools` сервиса на `PdoToolsWrapper` — Fenom требует строгий тип `CoreTools`, не работает с наследниками
- ✗ Реализация интерфейса `debugPdoParser` в парсере — проверка устарела и не работает в pdoTools 3.x

**Почему не работает:**
- pdoTools инициализирует свой внутренний парсер **до** того, как Modx3ProfilerToolbar пытается его заменить
- Fenom использует строгую типизацию и требует именно `CoreTools`, отвергая любые обёртки или наследников
- Все попытки перехвата приводят к `TypeError` или сбою Fenom

### 4. Почему не используется `CoreTools::$tags`?

**Причина:** Массив `$tags` (используемый в `debugParser()`) очищается **после каждого завершённого** вызова сниппета/чанка. К моменту `OnWebPagePrerender` в нём остаются только **незавершённые** вызовы (обычно пустой массив).

**Код в CoreTools.php:**
```php
// При первом вызове debugParser() — добавляется в $tags
$this->tags[$hash] = ['parse_time' => microtime(true), ...];

// При втором вызове debugParser() — удаляется из $tags
unset($this->tags[$hash]);
$this->modx->parser->tags[] = $data; // ← переносится в $parser->tags
```

**Результат:** `CoreTools::$tags` всегда пуст при `stop()`, нет данных для сбора.

## Альтернативы для полной интеграции

Для получения **полной** статистики (время выполнения, SQL-запросы) потребуется:

### Вариант 1: Патч pdoTools (не рекомендуется для продакшена)

Форкнуть pdoTools и добавить вызовы колбэков перед/после выполнения сниппетов:

```php
// В CoreTools::runSnippet()
public function runSnippet($name, array $properties = [])
{
    $start = microtime(true);
    if (isset($GLOBALS['Modx3ProfilerToolbarCallback'])) {
        call_user_func($GLOBALS['Modx3ProfilerToolbarCallback'], 'before', 'snippet', $name);
    }
    
    $result = ...выполнение сниппета...
    
    if (isset($GLOBALS['Modx3ProfilerToolbarCallback'])) {
        call_user_func($GLOBALS['Modx3ProfilerToolbarCallback'], 'after', 'snippet', $name, microtime(true) - $start);
    }
    return $result;
}
```

**Плюсы:** точное время, запросы, полный контроль  
**Минусы:** нужно поддерживать форк, конфликт при обновлении pdoTools

### Вариант 2: Экспериментальный патч ядра MODX

Добавить в `modX` глобальные хуки для `runSnippet()`, аналогичные системным событиям. Требует изменений в ядре MODX Revolution.

### Вариант 3: Обёртка на уровне приложения (текущий вариант)

Использовать доступные данные из `CoreTools::$timings` для подсчёта **количества** вызовов без точного времени. Этого достаточно для понимания, какие сниппеты работают и сколько раз вызываются.

## Рекомендации

**Для большинства случаев достаточно текущей реализации (вариант 3):**
- Видно, какие сниппеты выполняются
- Видно количество вызовов
- Общее время запроса (`⏱️`) и память (`💾`) корректны
- Стандартные MODX-теги (не через pdoTools) профилируются полностью

**Если критически важна детальная статистика по Fenom:**
- Форкнуть pdoTools с патчем (вариант 1)
- Или использовать отладочный режим pdoTools (`&showLog=1`) вручную

## Примечания

- Fenom **работает корректно**, профайлер не ломает его обработку
- Ограничения относятся только к **детализации статистики**, не к функциональности
- Все изменения изолированы в Modx3ProfilerToolbar, pdoTools не модифицируется
