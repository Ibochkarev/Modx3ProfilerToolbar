# Рекомендации по оптимизации производительности

Практические советы по использованию Modx3ProfilerToolbar и устранению узких мест, которые показывает тулбар.

---

## Чек-листы

### Перед деплоем на production

- [ ] **modx3profilertoolbar.sampling_rate** установлен на 1–5% (не 100%).
- [ ] Доступ к админке ограничен — тулбар показывается только при входе в Manager.
- [ ] **modx3profilertoolbar.frontend_toolbar** выключен для обычных пользователей или доступ только для разработчиков.
- [ ] Режим 100% профилирование отключён для production при высокой нагрузке.

### После оптимизации

- [ ] TTFB и Total time уменьшились на проблемных страницах.
- [ ] Количество SQL-запросов на запрос сократилось (нет N+1).
- [ ] Медленные сниппеты закэшированы там, где возможно.
- [ ] Нет или минимум срабатываний правил Advisor в тулбаре (некэш, N+1, медленные запросы, перегруз чанков).
- [ ] Накладные расходы профайлера в пределах ожиданий (< 5% при dev, < 0.5% при sampling на production).

---

## Как пользоваться тулбаром (workflow)

1. Включите **modx3profilertoolbar.enabled** и **modx3profilertoolbar.frontend_toolbar**, залогиньтесь в Manager.
2. Откройте страницу сайта — в правом нижнем углу появится панель с метриками текущего запроса.
3. Разверните тулбар: вкладки **Overview**, **Slow Components**, **Timeline**, **SQL** показывают, где ушло время и какие компоненты/запросы самые тяжёлые.
4. По рекомендациям Advisor (в тулбаре) устраняйте узкие места: кэш сниппетов, устранение N+1, индексы, уменьшение вызовов чанков.
5. Сравнивайте метрики до и после изменений (обновляйте страницу и смотрите новые значения в тулбаре).

## Интерпретация метрик

- **Performance Score (0–100):** падает при большом total time, высокой доле SQL, росте памяти и при срабатывании правил Advisor. Цель — стабильно высокий score на типичных страницах.
- **TTFB vs PHP time:** если TTFB сильно больше времени PHP — узкое место может быть до вывода (сеть, прокси, кэш, база до приложения). Если близки — оптимизируйте код и запросы.
- **Timeline:** длинные блоки между событиями MODX (OnHandleRequest, OnLoadWebDocument, OnWebPagePrerender) показывают, на каком этапе тратится время.
- **SQL count:** десятки и сотни запросов на один запрос страницы — повод искать N+1 и объединять выборки.

## Сниппеты (Snippets)

- **Кэширование:** включайте кэш для сниппетов с одинаковым результатом при одинаковых параметрах. В профайлере обращайте внимание на пометки «cached: no» для медленных сниппетов (Advisor: UncachedSnippetRule).
- **Параметры кэша:** задавайте разумный `&cache` или используйте системную настройку кэширования для Fenom.
- **Тяжёлые операции:** выносите тяжёлые выборки в отдельные сниппеты с кэшем; в основном сниппете только подставляйте готовые данные.
- **Избегайте лишних вызовов:** один вызов с полным набором параметров лучше нескольких подряд с разными.

Пример (концептуально): кэшируемый сниппет каталога:

```fenom
{* Кэш на 1 час для списка товаров категории *}
{'getProducts' | snippet : [
  'parents' => 10,
  'limit' => 20,
  'cache' => 3600
]}
```

## Плагины и события

- **Порядок событий:** тяжёлая логика в ранних событиях (например, OnHandleRequest) задерживает весь pipeline. Переносите необязательную работу в более поздние события (OnLoadWebDocument, OnWebPagePrerender) или в отложенную обработку.
- **Один плагин — одна задача:** несколько тяжёлых плагинов на одном событии суммируют время; по возможности объединяйте или отключайте неиспользуемые.
- **Advisor** может рекомендовать «перенести логику на более позднее событие» для плагинов с большим временем на ранних этапах.

---

## Чанки (Chunks)

- **Количество вызовов:** если один чанк вызывается десятки/сотни раз в одном запросе (Advisor: ChunkOveruseRule), пересмотрите циклы и шаблоны. Варианты: уменьшить размер выборки, кэшировать блок целиком, объединить чанки.
- **Fenom:** используйте кэш Fenom для тяжёлых шаблонов; компиляция и повторный рендер без кэша видны в Timeline.
- **Вложенность:** глубоко вложенные чанки увеличивают накладные расходы; по возможности упрощайте структуру.

## SQL

- **N+1:** один и тот же запрос в цикле (по одному на элемент) — типичная причина десятков запросов. Решение: одна выборка с JOIN или предзагрузка связей (например, `getCollection` с критерием по списку ID). Advisor помечает такие случаи (N1QueryRule).
- **Индексы:** медленные запросы (SlowQueryRule) часто упираются в отсутствие индексов по полям в WHERE, ORDER BY, JOIN.
- **Группировка:** если возможно, замените множество мелких запросов одним с группировкой или подзапросами.
- **Лимиты:** не выбирайте лишние строки; используйте `limit` и пагинацию.

Пример устранения N+1 (концепт):

```php
// Плохо: N+1
foreach ($products as $product) {
    $category = $modx->getObject('msCategory', $product->get('parent'));
    echo $category->get('pagetitle');
}

// Лучше: один запрос с JOIN или предзагрузка
$products = $modx->getCollection('msProduct', [
    'query' => [
        'leftJoin' => ['msCategory' => 'msCategory.id = msProduct.parent'],
        'select' => ['msProduct.*', 'msCategory.pagetitle as category_title']
    ]
]);
```

## Fenom

- **Кэш шаблонов:** включайте кэш компиляции Fenom для стабильных шаблонов.
- **Минимум логики в шаблоне:** тяжёлые вычисления и запросы лучше в сниппете/плагине с кэшем; в шаблоне — вывод и простые условия.

## Пороги Advisor

Настройки **modx3profilertoolbar.slow_snippet_ms** и **modx3profilertoolbar.slow_query_ms** задают пороги для рекомендаций Advisor в тулбаре (в миллисекундах).

- **Разработка:** оставьте значения по умолчанию (50 и 100 мс) или чуть ниже, чтобы видеть больше предупреждений.
- **Production:** повысьте пороги (например, 150 и 200 мс), чтобы Advisor выделял только действительно проблемные вызовы.

Подробнее: [Настройка](configuration.md#пороги-и-метрики).

## Окружение: разработка и production

| Аспект | Разработка / Staging | Production |
|--------|----------------------|------------|
| **modx3profilertoolbar.enabled** | Да | По необходимости (временно или с sampling) |
| **modx3profilertoolbar.sampling_rate** | 100 | 1–5 |
| **modx3profilertoolbar.frontend_toolbar** | По желанию | Нет (тулбар только при входе в Manager) |
| **modx3profilertoolbar.cli_enabled** | При отладке кронов | Нет |

На production не включайте 100% профилирование без ограничения доступа к админке. Подробнее: [FAQ](faq.md).

## Безопасность

- Профайлер выводит чувствительные данные: SQL, имена компонентов, метрики. Не открывайте доступ к админке посторонним — тулбар виден только при входе в Manager.
- Трейсы не сохраняются на диск и в БД — данные только в HTML текущего запроса.

## Типичные антипаттерны (что часто видно в профайлере)

- **Один медленный некэшируемый сниппет на каждой странице** — включить кэш или вынести тяжёлую логику в кэшируемый вызов.
- **Один и тот же SQL десятки раз с разными параметрами** — N+1; заменить на одну выборку с IN/JOIN.
- **Один чанк вызывается 50+ раз в одном запросе** — уменьшить цикл или кэшировать фрагмент вывода.
- **Плагин с большим временем на OnHandleRequest** — перенести логику на OnLoadWebDocument или позже; отключить, если не нужен на каждой странице.
- **Много мелких запросов вместо одного с JOIN** — объединить в один запрос с подзапросами или предзагрузкой связей.
- **Рост memory_peak на тяжёлых страницах** — проверить размер выборок, не держать в памяти лишние объекты, использовать пагинацию.
